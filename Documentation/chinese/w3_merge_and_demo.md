## 为什么旧 demo 不流畅

旧默认动态场景为 120.433 秒、90 张图，约 0.75 张/秒。行驶时通常每秒一张；扫描和恢复期间最长约 8.1 秒没有新画面。第三人称逐帧选择第一个无遮挡位置，会从机器人一侧突然切到另一侧。每次显示图片时才加载资源，也会增加等待。

新版录制在 30 Hz 控制步之间每两步采一帧，即真实 15 fps。转身、扫描、停车和恢复也持续录制，直接流式编码为 H.264 MP4；相机保留当前无遮挡侧，必要换位时限制相机移动速度。浏览器使用原生视频时间轴，默认 1×，图像回放保留为历史记录和兼容路径。视频的 RGB 预览不会作为额外检测证据交给 mapper。

新的连续视频先重录动态困难场景的 Nearest 条件；其他历史条件仍明确标为“历史稀疏图像回放”，没有把旧图重复编码后宣称提高实测帧率。运行其他条件时也会默认录制 15 fps，`--video-fps 0` 可关闭视频录制。

## 双向传递是否存在

已有两层处理：

1. A 更新深度地图；B 检查当前剩余路线。路线失效时先停止旧轮速命令，再对同一个目标重新规划。
2. 同一目标没有安全路径、持续接触、运动停滞或超出预算时，B 向 C 返回失败和原因；C 用新地图、新可达性评估、失败目标排除项和 `previous_attempt` 改选目标，再向 B 下发。

上层不必因每个可绕过的障碍都改换搜索目标。能局部绕行时由 B 保持原目标；无法绕行时才交给 C 改选。LLM 的请求载荷也包含 `previous_attempt`，但离线回放条件没有实际模型推理。

共享生产框架对应 `TeamNavigator.update_map()`、`_replan()` 和 `EpisodeRunner` 的 operation feedback/recovery；当前 Rs 演示对应 `Episode.follow()` 与决策循环。新版 demo 将关键过程写为独立 `feedback_flow` 事件，并支持页面时间跳转：

```text
A_to_B_route_invalidated
  → 停车
  → B_local_replan
  → [失败] B_to_C_replan_request
  → C_to_B_strategy_replan
```

原默认运行日志已存在 `F9 → blocked → F11` 和 `F13 → blocked → target_approach` 的真实反馈。不能把日志中的每次 blocked 都归因于动态推车；它也可能来自静态家具或进一步观测使原路线失效。

[原失败改选日志](../../runs/w3-merge-20261017/previous-demo/dynamic/nearest.jsonl) 和原图像均已备份。新版动态 Nearest 的一次真实运行在 74.267 秒内行驶 10.422 米，最终距目标 0.789 米，零接触，发生 1 次局部重规划；此次局部绕行成功，没有触发上层改选。[新单场回放](../../runs/igibson-w3-smooth-20261017/index.html) 和原展示入口均可查看。

新版视频实测为 1440×900、H.264、15 fps、1115 帧，最大采样间隔 0.066667 秒。已解码抽查视频画面，并验证浏览器控制逻辑；当前浏览器自动化运行时不可用，没有声称完成浏览器截图验收。
