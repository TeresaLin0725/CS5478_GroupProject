# A：深度融合计时与逐帧对照基线

第一阶段建立融合内部计时和逐帧对照基线；第二阶段优化 Python 射线循环与证据累计；
第三阶段优化采样像素读取和坐标转换。
分辨率、采样步长、深度范围、射线几何、净空判定和动态清除规则保持不变。
正常运行不启用分析器。原有最终栅格判定循环拆入 `_finalize_free_space`，用于区分耗时。

## 使用

对已有、带校验和的 RGB-D 序列运行：

```powershell
python scripts/profile_rgbd_fusion.py --dataset runs/locobot-full-scan-package-001 --output runs/fusion-before --repeats 3 --warmups 1
```

也可生成固定的 640×480 合成数据。它沿用当前集成入口的建图和机器人配置
（步长 4、动态清除连续帧数 2），但几何是解析地面、墙和可移除箱子，不能算原生仿真验收。
生成后应保留同一份数据包，后续比较不要重新生成：

```powershell
python scripts/make_fusion_fixture.py --output runs/fusion-fixture
python scripts/profile_rgbd_fusion.py --dataset runs/fusion-fixture --output runs/fusion-before --repeats 3 --warmups 1
```

每个输出目录必须是新目录，不覆盖历史证据。优化后用相同解释器、数据和设置比较：

```powershell
python scripts/profile_rgbd_fusion.py --dataset runs/fusion-fixture --output runs/fusion-after --repeats 3 --warmups 1 --baseline runs/fusion-before/baseline.json.gz
```

`--max-frames N` 只处理前 N 帧，保留它们的完整先前历史；前后比较必须选相同帧。
每次预热和测量都从重置状态顺序回放，不把同一帧反复融合到持续累积的地图里。

## 输出与计时边界

- `report.json`：不带分析器的逐帧耗时、中位数及最近秩 P95；独立分析器回放的阶段耗时；
  输入/配置/源码摘要、解释器信息、重复一致性、逐帧状态摘要、障碍清除事件和基线差异。
- `baseline.json.gz`：逐帧保存占据图、覆盖图、整列高度空闲位掩码、地面证据和动态清除计数。
  比较覆盖每个栅格，不能仅凭最终占据图相同就通过。
- `profiles/frame-*.prof`：标准 cProfile 文件，可用 `python -m pstats 文件路径` 查看。

时间只包围真实 mapper 中的 `fuse_observation` 调用，不含文件加载、mapper 校验/工作副本、
检测器、跟踪、前沿提取、序列化和证据比较。因此它不等于整个 `mapper.update()` 的时间。
阶段划分为：

1. `sampling_projection_s`：深度扫描、有效性/采样检查、坐标转换和标定校验。
   当前实现位于同一个生成器，暂不把采样与投影拆成两个数字。
2. `ray_traversal_s`：`_ray_voxels` 生成器运行期间的时间，不含挂起时调用方写证据的时间。
3. `map_finalization_s`：最终整图净空判定和动态清除。
4. `endpoint_evidence_and_other_s`：端点处理、射线证据写入、集合/字典更新及剩余循环/设置开销。

cProfile 的默认计时是分析器下的经过时间，不能当作未插桩的 CPU 时间。
它会显著放大 Python 调用与生成器成本；阶段占比只用于定位热点。
脚本单独报告其墙钟开销倍数，真实帧延迟使用不带分析器的回放。
缺少移动障碍的录制数据不能证明动态清除正确性。

基线输入或配置不同会在测量前拒绝比较；任一重复/分析器回放/旧基线的内部证据不同，
CLI 返回非零并保留差异报告。性能比值仍需结合机器负载和解释器信息判断。

## 第一阶段：2026-10-28 的基线验证

- 历史真实录制的前三帧：320×240、步长 1，Python 3.11.9；预热一次、三次测量。
  修改前后逐帧五类缓冲区完全一致。两次不带分析器的中位数约 1.96 / 1.95 秒，
  这只是诊断重构的一致性检查，不宣称提速。
- 固定 640×480、步长 4 的七帧合成序列：第一帧观察箱子；第二帧累计一次净空；
  第三帧重复时间戳不推进计数；第四帧箱子重新出现使计数归零；第五、六帧连续新证据
  后清除 10 个障碍栅格。另与 Git `fddec67` 的原始融合实现逐帧比较，五类缓冲区完全一致。
- 该合成序列初次测量中位数约 0.724 秒、P95 约 0.734 秒；分析器约放慢 3.25 倍。
  分析器阶段占比约为：采样/投影 13.9%、射线遍历 56.9%、最终判定 0.1%、证据写入等 29.1%。
  它与历史真实录制以及此前约 1.49 秒/帧的测量条件不同，不能横向计算提速。
- 最终工具复跑同一数据并读取上述基线：全部逐帧证据一致，中位数约 0.717 秒、
  P95 约 0.727 秒；射线遍历约占分析器耗时 57.1%，分析器墙钟开销约 3.26 倍。

本机原始结果保存在 Git 忽略的 `runs/fusion-profile-20261028-before/`、
`runs/fusion-profile-20261028-after/`、`runs/fusion-profile-640-20261028-v2/` 和
`runs/fusion-profile-640-20261028-final/`。
原始实现对照记录为 `runs/fusion-profile-640-20261028-v2/original-comparison.json`。

本轮相关测试共 58 项，57 项通过，1 项已有失败。
回归覆盖计时回放与直接 mapper 一致、逐帧证据差异、输入不一致拒绝比较、不覆盖输出、
固定场景中的真实动态清除、射线几何和 mapper 净空规则。
集成测试 `RecoveryViewpointTests.test_one_localized_view_can_propose_inspection_but_cannot_claim_success`
仍失败；已用 Git HEAD 的原始融合实现复现，属于已有的目标接近候选行为，与此次计时重构无关。

## 第二阶段：射线循环与证据累计优化

生产改动位于 `perception/fusion.py`，仍使用纯 Python，不增加依赖：

- 射线逐格推进改用三个轴的局部标量，减少每步 `enumerate` 对象、列表索引及列表转元组。
  保留裁剪、轴推进顺序、同时跨界处理、`1e-10`/`1e-12` 容差和上界截断规则。
- 动态清除的当前帧高度证据改用二维整数网格，避免每个射线栅格创建坐标元组并查找字典；
  每格的位移值只算一次。该网格每帧重建，未用历史累计证据替代当前帧证据。
- 位掩码继续使用 Python 任意精度整数，支持超过 64 个高度层。

同一 Python 3.11.9 解释器、同一七帧 640×480 数据包、步长 4，完整预热一次、测量三次，
共 21 个帧耗时样本；下表使用不带分析器的融合耗时：

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 中位数 | 0.721 秒/帧 | 0.529 秒/帧 |
| P95 | 0.743 秒/帧 | 0.537 秒/帧 |

中位数耗时降低约 26.6%，约 1.36 倍速度。它是该固定回放的结果，不等于整回合提速比例，
也不代表已在原生 Python 3.8/iGibson 环境复现相同收益。
分析器回放仍显示射线遍历占主要部分，后续可继续评估直接采样/批量投影或编译循环。

结果目录为 `runs/fusion-optimization-before-20261028/` 和
`runs/fusion-optimization-after-20261028/`。优化后报告的 `baseline_comparison`、
`repeat_checks` 和 `profile_matches_unprofiled` 均通过，五类缓冲区逐帧完全一致。
固定场景仍在第六帧清除 10 个障碍栅格。

新增 `tests/reference_fusion.py` 保存 Git `fddec67` 的原始融合算法作为独立测试对照，
不参与生产执行。`test_fusion_equivalence.py` 比较 5,000 条随机/边界射线的完整有序栅格序列，
并比较静态/动态模式、步长 1/4、多帧障碍出现/移除、空观测、禁止推进清除计数，以及
超过 64 位的高度掩码。全部对照一致。

另回放历史真实录制的前三帧（320×240、步长 1、动态清除关闭），优化后五类缓冲区与
第一阶段旧基线逐帧完全一致；本次中位数约 1.578 秒/帧，P95 约 1.645 秒/帧。
结果在 `runs/fusion-optimization-native-after-20261028/`。
它与前述合成数据条件不同；真实数据的旧计时来自第一阶段，未用其差值宣称同批次提速。

第二阶段全量回归命令：`python -m unittest discover -s tests`（`PYTHONPATH=src`）。
共 459 项：453 项通过、5 项因可选依赖缺失跳过、1 项为前述已有的目标候选过期测试失败，
没有新增失败。新增源码另通过 Python 3.8 语法解析检查；这不替代原生 3.8 环境运行验收。

## 第三阶段：直接采样与批量投影

生产改动位于 `perception/projection.py`，以提交 `254279b` 为本阶段起点：

- NumPy 可用时，以 little-endian float32 视图直接选取 `[::stride, ::stride]`，只检查采样像素。
  640×480、步长 4 时检查 19,200 个像素，避免扫描全部 307,200 个像素。
- 用 float64 批量计算相机和世界坐标。缓存像素索引与 `(u-cx)`、`(v-cy)` 偏移，
  保留原来先乘深度、再除焦距的顺序；世界变换逐项乘加，不用矩阵乘法或改变求值顺序。
- 缓存最多八组一维标定采样轴，数组只读。相机外参随每帧读取，不缓存机器人位姿。
  每批最多处理 64 个采样行，限制临时数组和 Python 列表大小。
- 无 NumPy 时，使用 `Struct.unpack_from` 直接读取采样像素，仍使用相同缓存偏移和标量公式。
  不添加强制依赖；普通运行自动选择可用路径。
- 保留正有限深度筛选、像素行优先顺序、Python 标量输出类型，以及溢出时先返回此前有限点、
  再抛出 `ContractError` 的行为。直接调用投影器时也明确校验步长为正整数。

第三阶段测试用 `tests/reference_projection.py` 保存 `254279b` 的旧投影器；
`reference_fusion.py` 同时改用这份旧投影器，避免新旧融合对照实际共享被优化代码。
对两种执行路径逐点比较浮点数 `.hex()`，包含奇数尺寸、跨批次大图、不同标定和步长、
非有限/负/零深度、极小/极大 float32 深度、溢出和 NumPy 错误策略恢复。缓存只读和容量也有检查。

同一 Python 3.11.9、NumPy 2.4.6、同一七帧数据包，旧/新投影器分别预热一次，
在同一进程内以旧→新、新→旧、旧→新顺序交替测量；每次从重置状态完整回放，
每种实现各有 21 个不带分析器的融合帧样本：

| 指标 | 提交 254279b 的投影器 | 本阶段 NumPy 投影器 |
|---|---:|---:|
| 融合中位数 | 0.546 秒/帧 | 0.450 秒/帧 |
| 融合 P95 | 0.553 秒/帧 | 0.455 秒/帧 |

中位数耗时进一步降低约 17.5%。交替测量用于减小系统负载随时间变化的影响；
结果仍只适用于该固定序列和解释器，不等于整回合提速或原生 Python 3.8 验收。
各次回放五类地图/证据逐帧一致，单独禁用 NumPy 的七帧回放也完全一致。

独立的工具测量同样通过基线对照；采样/投影在分析器下的耗时从约 0.314 秒降至约 0.016 秒，
但阶段数值受分析器影响，不能将其直接当作不插桩耗时。射线遍历仍为主要热点。
历史真实录制前三帧（320×240、步长 1）的五类缓冲区也与旧基线一致；
本次中位数约 1.463 秒/帧，不将不同解释器路径和批次的历史计时用作严格性能对照。

- `runs/projection-optimization-paired-20261028.json`：交替测量原始耗时、源码摘要及逐帧一致性。
- `runs/projection-optimization-native-20261028/`：历史真实录制回放。
